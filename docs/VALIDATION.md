## What the automated tests prove

`tests/platform.test.ts` exercises actual HTTP requests, cookies and a temporary SQLite/file store, including:

- registration, real sessions, server roles, logout and Origin rejection;
- Unicode case-insensitive maker/project city search, including Cyrillic;
- stale revisions, immutable terms and concurrent selection of different offers;
- private briefs and denial of attachment reads before/after assignment for unrelated users;
- provider delivery followed by customer-only completion;
- 512 messages, access to old/new pages and a bounded read cursor;
- original model rights, private pending files and moderator publication;
- expiring one-use recovery and session revocation;
- admin activation only on redemption of an operator-issued token, with old-session revocation;
- account-removal refusal for active deals and explicit retained-history anonymization;
- malformed files, ownership, referenced-file cleanup protection, private export;
- a stopped-instance database/files backup, integrity check, file-hash check, restore, and corrupted-file rejection.

`tests/parts.test.ts` checks positive valid dimensions, rejected impossible walls/heights, exact money parsing, closed two-face edge incidence and analytical volumes for block, drilled plate and tube meshes.

`tests/studio.test.ts` covers real HTTP/session ownership, whole source-idea preservation within the accepted length, CAS, confirmation history, preserved unresolved questions, exact immutable STL bytes, concurrent publication and rejection of changed publication parameters. It also checks non-FDM workshop matching, complete mixed-process handoff, history limits, additive migration and reopening, export/account closure, and retained usage after a project is deleted.

`tests/cad.test.ts` exercises actual HTTP sessions and SQLite with an injected deterministic compiler transport. Its eleven tests cover strict schemas; ownership/Origin/version conflicts; request replay; exact confirmed artifact handoff; direct recipients, quotation grants, revocation after profile unpublication and accepted-provider access; stale completion; editing a confirmed CAD revision; cancellation/timeouts; persistent attempt and storage limits; rejected missing/tampered/spec-mismatched/mesh-mismatched artifacts; account deletion during a build; queued restart and interrupted work; CAD BLOB backup/restore; and v2→current migration with existing confirmations. These transport fixtures establish application state and permissions, not native geometry correctness.

The separate Python suite runs the actual CadQuery/OpenCascade kernel: analytic volumes, STEP round-trip, distinct assembly components and transforms, extrusion/fillet/chamfer, intersections, declared missing geometry, bounding boxes, mesh indices, artifact hashes, strict input limits, CSV formula protection and atomic CLI failure. `scripts/cad-check.mjs` compiles the actual plate/shelf examples and passes their files through the Node validator. Passing a geometric check does not establish physical strength, manufacturability or completeness of the declared design.

AI tests inject a deterministic test transport into the real server. They check the fixed Responses endpoint, strict schema, selected model, explicit consent, request deduplication, attempt limits, two-call instance concurrency, provider refusal, timeout, incomplete response, stale edits/confirmation, withheld invented dimensions and account closure while a call is running. They establish application behavior under these fixtures, **not live model quality or provider availability**. The earlier validation on 2026-11-14 used the actual `database.ts` from the original 0.1 implementation to create a v1 database; migration and reopening preserved existing data and passed SQLite foreign-key checks. The current suites cover v1/v2/v3→v4 fixtures, supplemented by the historical v0.2 implementation check above.

`tests/cad-ai.test.ts` adds twelve cases for private immutable proposals, separate reviewed application, shared brief/CAD quotas, task-bound request IDs, stale source detection, question-only output, schema/token/input/storage bounds, history limits, timeout/oversized response handling, account closure and v4 migration. The native integration case applies a deterministic AI proposal, builds it through the actual CadQuery worker, checks the report and confirms the exact artifact hashes in the handoff packet. The outgoing JSON-schema projection is inspected locally; acceptance of that schema by a live provider has not been tested.

Seven browser tests use the real application API with fictional data and the built frontend. Two additional AI-proposal tests mock only the proposal endpoints; authentication, brief editing, CAD persistence and publication use the real API. `scripts/e2e.mjs` starts a fresh server and temporary database for each spec file and combines the evidence into one HTML report. The native assembly flow requires `CAD_PYTHON`; without it, eight tests run and that one flow is skipped. `OPENAI_API_KEY` is explicitly empty in the browser-test server environment. Test artifacts and private tokens stay outside version control.

An initial combined nine-test run passed six and failed three after exhausting the shared test server's IP rate limit. Traces showed a normal number of requests within the failing test and accumulation across previous scenarios. Spec-level server isolation fixed the harness coupling and all nine passed on the rerun; the production limit remains unchanged. Interrupting the new runner with SIGTERM while the server was active returned exit 143 and closed the server port. An earlier Linux pytest run hit an environment-size error because a large parameter value was copied into `PYTEST_CURRENT_TEST`; explicit short parameter IDs fixed the fixture, and the rerun passed all 28 native tests. These initial harness failures are not counted as successful runs.

## Not established by these checks

No physical model printing, actual commercial deal, public adoption, production traffic benchmark, multi-process load test, independent penetration test, manual screen-reader evaluation, native iPhone/Android check, Safari/Firefox automation or complete locale/content review has been performed. The optional external OSM tile service is not guaranteed to be available. Real deployment DNS/TLS, operator recovery procedures, backup scheduling and off-site restoration depend on each installation.

No live paid OpenAI call was performed. No API key was configured in this workspace. Manual declarative CAD, assembly generation and the optional AI proposal/review/application pipeline are implemented and checked as described above. Arbitrary STEP import into editable feature history, CAM/G-code, FEA, machine-profile validation, automatic multi-agent task routing, monetary budget accounting and multi-provider work orders are not implemented. Configuring a model name and receiving a structured test response do not establish that the selected model is available to an operator or that its engineering output is correct. See [AI_EVALUATION.md](AI_EVALUATION.md) for the bounded operator-run live check.

The initial overview does not load Three.js or Leaflet. Three.js is loaded with the relevant tools/CAD preview and still produces Vite’s >500 KB raw-chunk warning. No measured Lighthouse/Core Web Vitals claim is made. Native-process resource limits are not evidence of a complete filesystem/network sandbox, especially on macOS where the Linux virtual-memory cap is not applied.
